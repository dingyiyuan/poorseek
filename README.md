# poorseek

**一个只为一种配置维护的 DeepSeek-V4.1 推理框架：Intel Arc Pro B70（32 GB 显存）+ 192 GB 主机内存，SYCL 后端。**

> **非官方、个人项目。** 这不是上游项目的分支，也不跟随任何上游的发布节奏；它只为我这一台机器的配置更新。
> 不提供通用安装支持，不承诺接口稳定。想参考哪一块直接取用，不必等我合并什么。

## 目标配置

| | |
|---|---|
| GPU | Intel Arc Pro B70，32 GB 显存（Battlemage / BMG-G21） |
| 主机内存 | 192 GB DDR5 |
| 模型 | DeepSeek-V4.1-Flash，MoE（40 层，每层 384 个路由专家，共 15 360 个） |
| 后端 | **SYCL**（oneAPI / Level Zero） |
| 上下文 | 384 K |

32 GB 显存放在哪里都不够放全部专家：显存里只留最热的约 1 500 个专家，其余走主机内存与 CPU 车道。这个项目围绕这一个事实来做取舍。

## 状态

早期、自用。**SYCL 引擎就在 `main` 的 `sycl/` 里**（此前 Rust 侧的 `xolotl-sycl-*` 分支是更早的一次尝试，已被它取代）。
Vulkan / Metal / CPU 后端在 `crates/` 里，作为控制面与后续扩展的底座保留。

## 同机参考数据

在同一台机器（Arc Pro B70 32 GB + 192 GB DDR5）上跑 DeepSeek-V4.1-Flash IQ2_XXS（384 K 上下文、40 层、15 360 专家）的实测值：

| 场景 | 实测 |
|---|---|
| 解码（真实多样 prompt：短-中文 128 / 长-英文 512 / 中-中文 256） | **19.5 / 23.2 / 20.5 tok/s** |
| 解码（同一 prompt 重复跑，专家全热） | 26–27 tok/s |
| **预填充 62.3 K token（两段式，2026-11-03）** | **957 tok/s**（同一段提示、融合路径 376 tok/s） |
| **预填充 132 K token（两段式，2026-11-03）** | **487 tok/s**（融合路径 273 tok/s） |
| **预填充 45.6 K token** | **347 tok/s**（345.0 / 348.4 / 348.4，三次）※改前 |
| **预填充 122 K token** | **271 tok/s**（优化前 168）※改前 |
| **预填充 200 K token** | **267 tok/s** ※改前 |
| 解码 @81 K 上下文 | 12.6 tok/s |

规模换算：100 K 输入约 **3.5 分钟**（132 K 实测 487 tok/s → 271 s）；62 K 是 957 tok/s。

### 2026-11-03：专家内核「每份权重只解一次」——端到端 **2.54×**（62 K）/ 1.79×（132 K）

MoE 专家内核按 64 个激活行切一块，每块都把同一份专家权重重新解量化一遍：457 行/专家就是 8 遍，
900 行是 15 遍。改成每专家只解一次到 f16 + 一次 oneMKL f16 GEMM（落在 XMX 上）之后：

| 提示 | 融合（每块重解） | 两段式（只解一次） | 加速 |
|---|---:|---:|---:|
| 62,289 token | 165,433 ms（376.5 tok/s） | 65,077 ms（**957.2 tok/s**） | **2.54×** |
| 132,068 token | 484,041 ms（272.8 tok/s） | 271,159 ms（**487.0 tok/s**） | **1.79×** |

专家阶段本身：62 K 111,674 → 12,179 ms（**9.17×**），132 K 257,038 → 45,109 ms（5.70×）。
单类型吞吐 4.2–7.2 → **33.9–51.8 TFLOPS**，这就是「library f16 GEMM 真的落在矩阵单元上」的直接证据
（融合路径那 4.2 TFLOPS 是 F32 SIMT）。

测量口径：同一份二进制、只差一个 env；每个长度跑**四次、两种顺序**（融合先 / 两段式先），
每次请求带唯一尾巴保证 `0 reused`。同一配置内部差 < 1%，组间 2.5×：

```
62K   融合     165,971 / 165,433 / 166,217 / 164,973 ms   375.3 / 376.5 / 374.7 / 377.6 tok/s
      两段式    65,978 /  65,077 /  65,652 /  65,072 ms   944.1 / 957.2 / 948.8 / 957.2 tok/s
132K  融合     485,660 / 484,041 ms    271.9 / 272.8 tok/s
      两段式   271,950 / 271,159 ms    485.6 / 487.0 tok/s
```

> 两次翻车也记在这里，因为比数字有用：
> ① 先说「开关没接管」——量的是 11-02 20:30 编的二进制，里面根本没有这段代码（代码 11-03 09:52 才提交），
> 所以 env 里那行开关是彻底的 no-op，所有守卫从未被求值。**判「开关无效」前先 `strings <bin> | grep <env 名>`。**
> ② 再说「2.51× 是缓存预热」——A/B 脚本切换配置时只清了三个开关、没清这一个，反序跑时「融合」腿
> 继承了上一腿的开关，**两条腿都在跑两段式**，于是「没有差异」，于是把真结论撤回了。
> **A/B 脚本里每一个开关都必须在切换函数里显式清掉**，靠「这次没设置就等于关」不成立。

为什么长上下文只有 1.79×：专家已经不是墙了。62 K 剩余时间里 sparse attention 36%、专家 29.5%；
132 K 是 compressor + indexer 30%（82 s）、sparse attention 18.6%、专家 16.7%、q_b + rope 15.3%。
**下一刀在注意力侧**，继续磨专家内核没有意义。

开关与安全：`DS4_EXP_2PHASE=1`，行数门槛 `DS4_EXP_2PHASE_MINROWS`（默认 96，解码绝不进去），
**生产已开**；接管了会打 `two-phase gate/up:ACTIVE`，没接管会打 `NO-TAKEOVER: <原因>`，
这样"静默不生效"不可能再发生。数值：7 种量化对拍全 `ALL OK`，最差 3.61e-04（容差 1e-02），
且**比融合路径更接近双精度参考**。

## 已知的墙（测出来的，不是猜的）

- 真实负载下 **40% 的时间在等 CPU 车道**（约 110 个专家/token 只能从主机内存来）；CPU 车道已经跑在内存带宽上（约 38 GB/s，本机 DDR5 纯读实测 49–51.6 GB/s），**没有余量**。
- 稠密投影每 token 要把 6.2 GB 权重重读一遍，卡在显存带宽（约 483 GB/s），**也没有余量**。
- 投机解码（DSpark/MTP）在本机**不划算**：接受率 100%、草稿只要 7 ms/轮，但验证一步 285 ms，因为 6 个 token 的窗口每层要 36 个专家而不是 6 个。唯一能翻正的场景是显存大到让窗口的专家全部驻留。
- **长上下文的预填充曾经慢一半**，原因不是同步而是注意力 slab 的批大小按剩余显存自动收缩：
  `DS4_ATTN_SLAB=2048` + `--vram-experts 1.0` 之后 122 K 从 168 → 271 tok/s（`q_b+rope` 一项从 42.9% 降到 8.8%）。
- 每层解码约有 5–10 个内核串行发射，**GPU 有一半时间在等发射**（验证窗口实测 GPU 忙 50%，单 token 路径接近 100%）。

## 阶段感知混合精度（预填充 / 解码分开配置）

DeepSeek 官方 checkpoint 里的路由专家是 **FP4(E2M1) + E8M0/32**，与 ggml MXFP4 同构，引擎已有该格式的内核。
所以我们把**前 20 层专家换成官方 FP4、后 20 层保持 IQ2**，打成一个"预填充专用包"：

| | IQ2 包（生产） | 混合包（L0–19 官方 FP4） |
|---|---|---|
| 专家内核耗时（122 K 预填充） | 72.7 s | **56.8 s（−22%）** |
| 122 K 预填充（端到端参考） | 367 tok/s | 416 tok/s |
| **解码** | ~21 tok/s | **6.74 tok/s（不可用）** |

解码掉到 6.74 的原因：MXFP4 每专家 blob 18.80 MB vs IQ2 的 7.74–10.23 MB，
显存按最大 blob 分槽 → 驻留槽位从约 40/层掉到约 25/层，大量专家改为从盘读。

**所以它只当预填充包用**，解码换回 IQ2。切换靠引擎自带的会话存档（含 KV）：

```
① 混合包 → 预填充 → slot_save（含 KV）
② 换 pack，重启引擎（约 10 s + 60 s 安全冷却）
③ IQ2 包 → slot_load → 解码（21 tok/s，原样）
```

已实测 **KV 可以跨 pack 承接**：换包重启后 839 token 的请求有 **822 个复用**，只新读 17 个
（专家格式不同，但 KV 布局与它无关）。工具：`tools/dsv41/two_phase.sh`、`tools/dsv41/mixed_pack.py`。

已经内置按长度自动决策（`TWO_PHASE_MIN_TOKENS`，默认 **15000**）：

| 提示长度 | 走什么 | 理由 |
|---|---|---|
| < 15 K token | **单段式（IQ2）**，不切换 | 混合包的 +12% 抵不过切换的 5 s |
| ≥ 15 K token | 两段式 | 预填充省下的时间超过切换成本 |

盈亏平衡点算法：切换 5 s ÷ (1/367 − 1/416) tok/s ≈ **15,600 token**（367 = IQ2 的 122 K 参考值，416 = 混合包）。
提示长度用 `字节数/3` 估算、阈值留了约 2 倍余量，估偏也不会做错决策。**切换开销实测 4.5–6 s**（不是估计值）：

| 步骤 | 耗时 |
|---|---|
| 引擎退出（进程消失） | 14–56 ms |
| 保险等待（`TWO_PHASE_SETTLE_MS`，默认 1000；实测 500 也安全） | 0.5–1 s |
| 服务就绪（HTTP 健康检查） | 0.8–2.2 s |
| **单次切换合计** | **4.5–6 s** |

一开始脚本里写的是固定 `sleep 60` 的冷却；换成"轮询真实条件"（引擎退出 + 端口就绪）后省下 52 秒。
显存没有可读的 sysfs 路径（`mem_info_vram_used` 在这台机上为空，也没有 `xpu-smi`），所以那一步只能退化成固定等待——
这是整个切换里唯一不是"等真实条件"的部分。

> 精度上不亏：前 20 层从 IQ2 提升到官方 FP4，后 20 层不变；而且实测 **IQ2 解码不比 Q4 笨**——
> 12 道硬题 11/12 vs 全精度 12/12，唯一差异是我的答案提取器（12 道硬题 11/12 vs 全精度 12/12，唯一的差异是我的答案提取器把 `9 sheep are left`
> 读成了 `left`）。IQ2 的量化损失要上千道题才测得出来，与文献里 GSM8K 上 1–4 分的量级一致。

工具链（都在 `tools/` 下）：`mixed_pack.py`（safetensors→混合包，逐位校验 max err = 0）、
`two_phase.sh`（两段式编排）、`overnight/gpu_lock.sh`（多 agent 时的 GPU 独占锁）、
`iq_bench.py` / `iq_hard.json`（可自动判分的智商基准）。
