# dsv41 解码：PCIe 双通道实测否决 + 专家放置规则实测收益（2026-11-03 晚）

承接 `docs/DECODE_HANDOVER.md` §3.4 的验证顺序。本文只写**实测**，每条都附命令与原始数字。
所有解码数字来自引擎自报（`decode: N tokens in X ms`）与 `DS4_PROF` 阶段表，短上下文用 CLI 直跑
（16-token 提示，`--n 128/256`），长上下文用 server + 45K 提示。

## 0. 结论（先看这个）

| # | 命题 | 结果 | 判定 |
|---|---|---|---|
| 1 | §3.2「CPU 车道 + PCIe→VRAM 双通道能把 38 GB/s 抬到 73」 | PCIe 在本引擎路径里只有 **≈6 GB/s**（单队列、每专家一次 memcpy、与计算同队列串行），把专家全交给它 → **2.9–3.2 tok/s** | ❌ **作废** |

## 1. 实验一：PCIe 通道到底有多快（否决 §3.2）

`DS4_DECODE_GPU=1` 是本仓已有的「专家经 PCIe 搬进 ring、由设备算」路径
（`ds4_model.dp.cpp` `decode_gpu_stage/kick`）：服务线程把每个专家的三块 memcpy 进 pinned staging，
主机侧再 `s->memcpy` 进 ring slot 并改 plan 行。生产配置是 `--ssd-cache 0`，该路径**默认关**。

同一二进制、同一 prompt、只差一个 env（16-token 提示，`--n 128`）：

| 跑次 | env | 解码 | ms/token | 车道专家 | `experts gate/up` |
|---|---|---:|---:|---:|---:|
| base1 | — | 22.93 tok/s | 43.99 | 4499/30480 (14.8%) | 4.94 ms |
| **gpu1** | `DS4_DECODE_GPU=1` | **2.94 tok/s** | **338.23** | 0 | **309.95 ms** |
| **gpu2** | `DS4_DECODE_GPU=1` | **3.16 tok/s** | **314.41** | 0 | **286.08 ms** |
| base2 | — | 24.28 tok/s | 41.19 | — | 5.04 ms |

换算：240 个专家/token × ≈8.4 MB ≈ **2.0 GB/token**，314–338 ms → **≈6.0–6.4 GB/s**。
这就是「一次 memcpy 一个专家、全在 in-order 计算队列上」的真实速率（与文档里的单队列探针 9.5 GB/s 同量级）。

**为什么这不是「换更深队列就能救」**：即使按 hotpin 深队列实测的 35 GB/s 算，2.0 GB/token 也要 **57 ms**，
已经比现在的整 token 37 ms 更长；而 CPU 车道读同样字节只要 ≈10 ms（21 个专家 × 0.3 ms 里含读+算）。
两条通道**不是「38+35」相加**——PCIe 侧 DMA 的源仍是同一块主机内存，主机带宽并不因此变宽。
§3.2 的算式把「主机内存读」和「PCIe 传输」当成两条独立带宽，这一点在 B70 上是错的。

判据（文档 §3.4 步 1 的写法）：PCIe 不是「接近饱和所以别用」，而是**用它更慢 8 倍**，所以 3.2 作废，
直接进 3.3。

## 2. 实验二：`DS4_LANE_NOHELP`（补上 §2.2 第 3/4 条的解释）

| env | 解码 | ms/token | 车道等待 |
|---|---:|---:|---:|
| — | 22.93 tok/s | 43.99 | 10.62 ms |
| `DS4_LANE_NOHELP=1` | **24.46 tok/s** | 40.99 | 7.88 ms |

主机线程不帮忙反而更快 → 车道的吞吐来自它自己的池；「38 GB/s」不是主机份额造成的假象，
也不是靠加线程能改善的。§2.2 第 3/4 条到此闭合：**车道是它自己那条路径的带宽/延迟，换核数无用**。

## 3. 实验三：专家放置规则（§3.3）

### 3.1 先看真实的解码路由有多尖

`DS4_TRACE` 抓 256 个解码 token 的路由（10240 条记录，65040 次挑选）后离线算（`/tmp/prof_from_trace.py`）：

| 放置方式 | 预测命中 | 车道占比 |
|---|---:|---:|
| 无 profile（按 index 放 0..39） | **10.9%** | 89.1% |
| 每层 top-40（profile 热度序） | **97.3%** | 2.7% |
| 跨层背包（`DS4_HEAT_BUDGET`） | 97.7% | 2.3% |

结论：**解码路由比预填充尖得多**——每层 384 个专家里前 40 个就吃掉 97%。§3.3 里「单层内不尖锐」的
结论来自预填充，对解码不成立。

### 3.2 A/B（n=256，每配置两次，只认后一次）

| 跑次 | 配置 | 解码 | ms/token | 车道专家 | swaps |
|---|---|---:|---:|---:|---:|
| ctrl | 生产配置 | 25.89 tok/s | 37.29 | 5489/61200 (9.0%) | 716 |
| **prof** | + `--expert-profile`（本 trace） | **26.79 tok/s** | **36.21** | **2147 (3.5%)** | 273 |
| profh | prof + `DS4_HEAT_BUDGET=1` | 26.59 | — | 1668 (2.7%) | 219 |
| prof2 | prof 复跑 | 26.68 | 36.32 | 1874 (3.1%) | 208 |
| ctrl2 | 生产配置复跑 | 25.49 tok/s | 37.91 | 5348 (8.7%) | 714 |

**+3.5~4% 解码，车道专家降到 1/2.5，换入换出从 716 降到 ~250。** 收益小于「车道专家少了 61%」的原因是：
车道的计算有相当一部分与同层 GPU 工作重叠，只有尾巴暴露成 `cpu-lane wait`（5.1 → 4.0 ms）。

### 3.3 怎么在生产用上

生产 `strata-server.json` 的 args 里没有 profile。加两行即可（serve 模式会持续学习并在退出/每 N 分钟写盘）：

```
--expert-profile <pack>/profile.bin --expert-profile-save <pack>/profile.bin --expert-profile-save-every 10
```

首轮冷启动会边跑边学（车道专家数会从 ~9% 降到 ~3.5%），之后每次启动直接吃学到的排名。

| experts gate/up | 5.45 | 6 专家 × m=1 |
| cpu-lane wait | 4.10 | 设备自旋等车道（profile 后） |
| down + post | 4.99 | |
| sparse attn | 1.89 | |

合计 ≈36.3 ms/token。GPU 在单 token 解码里接近满忙（见 `docs/MTP_STATUS_2026-11-01.md` §二十一），
所以剩下的空间只有「同样的字节用更少的 GPU 时间」——即 m=1 的效率，或者一次喂多个 token（MTP 窗口路径

## 5. 短上下文的钱花在哪之后：下一步（按性价比）

1. **把 profile 进生产并用长上下文验收**（本文的 45K 数字见 §6）——零代码，收益确定。
2. **`routing + shared` 5.7 ms**：shared expert 的权重读只值 ~0.08 ms（MTP 文档的账），这一格是唯一
   「确定还有收益」的软件项（~5%）：把 gate GEMV + route_publish + shared 的 3 次派发合成 1 次。
3. **m=1 的瘦 GEMM**（attn proj + attn tail ≈13.3 ms，36%）：要么合并 layer 的 kernel，要么换掉
   单行 GEMV 的 tiling。这是真正的 2× 级空间，但要动内核。
4. 不再碰：PCIe 双通道（§1 否决）、MTP 窗口（天花板=基线）、加线程（§2）。

## 6. 长上下文（62,289-token 提示，server API，128 token 解码）

协议同 `tools/overnight/ab2ph_clean.py`：每配置两次，只认后一次（热），每次请求带唯一 nonce。

| 跑次 | 配置 | 预填充 | 解码 | 车道占比 |
|---|---|---:|---:|---:|
| base-warm | 生产配置 | 64,740 ms (962 tok/s) | 64 tok in 5,086 ms = 12.58 tok/s | 0.1% |
| **base-hot** | 生产配置 | 64,137 ms (971.5 tok/s) | **64 tok in 3,593 ms = 17.81 tok/s（56 ms/token）** | 0.2% |
| prof-warm | + profile（同工作负载学到） | 64,951 ms | 64 tok in 87,321 ms = **0.73 tok/s** | 0.1% |
| prof-hot | 同上 | 64,117 ms | 64 tok in 4,480 ms = 14.29 tok/s | 0.2% |
| store-warm | + `--ssd-cache 16`（RAM store） | 65,735 ms | 64 tok in 16,372 ms = 3.91 tok/s | 0.1% |
| store-hot | 同上 | 106,085 ms | 64 tok in 42,919 ms = 1.49 tok/s | 0.2% |

**结论一：长上下文里 CPU 车道几乎不出场（0.2% ≈ 0.5 个专家/token），profile 无从发挥。**
62K 的 trace 里每层 top-40 只覆盖 76.6%（短上下文是 97.4%）——解码路由随上下文变宽，
但运行期的自适应换入仍把命中率顶到 99.8%，所以放置规则在长上下文上不是杠杆。

**结论二（更重要）：长上下文的解码时间被「冷专家读盘」主导，而且是**方差**主导。**
62K 预填充要把 118 GB 专家流一遍，page cache 被冲干净；之后解码每 token 只缺 0.5 个专家，
但每个冷专家要 ~1 s（`cpu-lane wait` 的累计平均在坏跑次里是 **1328 ms/token**，好跑次 36 ms）。
这解释了生产日志里那个飘忽的「27–33 ms cpu-lane wait」，也解释了为什么九轮优化都在噪声里打转。

**结论三：`--ssd-cache`（RAM store）在这台机器上是负收益**（3.9 → 1.5 tok/s，预填充也退化到 106 s）：
12.1 GB 的 store 只装 1557 个专家，而它挤占的正是页面缓存本来就装着的热专家（当时只剩 3 GB free）。

### 6.1 一条方法论修正（会坑后面所有人）

`DS4_PROF` 的 per-token 阶段表是**引擎生命周期内的累计平均**，不是单次请求的。A/B 里如果前一次跑次很慢
（本例 87 s / 64 token），它的坏数字会一直摊在后一次的表里（prof-hot 表里 `cpu-lane wait 793 ms` 而它
自己只跑了 4.5 s）。**A/B 只认引擎自报的 `N generated in X ms (Y tok/s)`**，阶段表只用来在单次干净跑次里看结构。

## 7. 长上下文真正该做的事（下一轮）

1. **把「每 token 的冷专家读」变成预取或预算**：现在 0.5 个专家/token × 1 s 就能吃掉整个 token 的时间预算。
   可选：按 profile 的热度把每层前 N 个专家**常驻 RAM**（不是 store，是 mmap 常驻），或者给车道加
   「每 token 冷读上限」，超了就退化成用邻居近似（需精度验证）。
2. **`routing + shared` 7.0 ms / token（长上下文）**：三层派发（gate GEMV → route_publish → shared expert
   gate/up → swiglu → down）合成一到两次，是文档 `MTP_STATUS` 里也点名的「确定还有收益的软件项」。
3. 短上下文侧可以叠加：profile（+3.5~4%）进生产配置。

## 8. 62K 复核（干净协议：每配置 3 次请求，r1 付首轮预填充，只认 r2/r3）

| 配置 | r2 | r3 | 均值 | 相对基线 |
|---|---:|---:|---:|---:|
| 生产配置 | 17.51 | 17.72 | 17.62 tok/s | — |
| `DS4_AHEAD=1`（下一层专家预取） | 16.93 | 17.29 | 17.11 tok/s | **−2.9%** |
| `+ --expert-profile` | 17.84 | 18.15 | **17.99 tok/s** | **+2.1%** |

- 所有配置的 **r1 都是 ~12.5 tok/s**（64 token 比 r2/r3 多花 ≈1.5 s ≈ **23 ms/token**），
  这就是 §6 说的「冷专家读盘尾巴」，而且**每次预填充之后都会重来一遍**——真实用户的长请求正好吃这一口。
- `DS4_AHEAD=1` 无效：它只是 `madvise` 预取到 page cache，而一次冷读要 ~1 s，提前一层（~1 ms）根本藏不住。
- 上一轮那个 0.73 tok/s 的异常跑次**没有复现**（这次 prof 配置 r1 就有 14.14 tok/s），判定为当时 DS4_TRACE +
  上一次 store 实验留下的内存压力造成的伪影。

## 10. 又否掉一条：`--mmap-experts off`（专家复制进 RAM，抗 page cache 淘汰）

假设：62K 预填充把 page cache 冲掉，解码的冷专家从盘上读 ~1 s；把 118.4 GB 专家复制进**不可淘汰的匿名内存**
应该能消掉这条尾巴。实测（同一 3 次请求协议，只认 64-token 那一次的主解码）：

| 配置 | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---:|---:|---:|
| 生产配置（`auto`） | 12.53 | 17.51 | 17.72 |
| `--mmap-experts off` | 13.33 | **13.21** | **13.60** |

**更慢（−24%）**：复制确实用掉 118.4 GB（载入 +32.7 s），但剩下的可用内存只够装下专家，
**稠密权重（attention/shared，每 token 都要读的那 1 GB）被挤出 page cache**，于是 attn proj / attn tail 从盘上读——
用一个更大的损失换掉了一个小损失。判定：**不开**，生产继续 `--mmap-experts auto`。

## 12. 主机侧时间 vs GPU（本轮加了仪表后实测）

给 `DS4_PROF` 的每 64-token 打印加了一行 `ds4 host: X ms/token in the layers`（`ds4_model.dp.cpp` 的
prof 打印块，增量计时；编一次 15 分钟）。短上下文 256 token：

| 跑次 | 主机层内时间 | GPU 事件合计 | 其中 cpu-lane 自旋 | 墙钟 |
|---|---:|---:|---:|---:|
| 无 profile ×2 | 31.75 / 32.60 ms | 37.28 / 37.24 ms | 5.22 / 5.04 ms | 38.4 ms (25.95 tok/s) |
| 匹配 profile | 33.20 ms | 36.66 ms | 4.06 ms | 37.7 ms (26.48 tok/s) |

**结论：主机 32 ms ≈ GPU 计算 32 ms（37.3 − 5.2 自旋），两条腿一样长。**
所以「只减派发」或「只改内核」单独做都没有收益——必须同时减；唯一真正的空闲是那 5–8 ms
**GPU 自旋等 CPU 车道**（占 token 15–20%）。这也解释了为什么此前所有单点优化都落在噪声里。

## 13. profile 必须与工作负载匹配，否则是负收益（已回退生产配置）

同一个二进制、同一协议（256 token，短上下文，跑两次基线确认稳定在 25.95）：

| profile | 短上下文 | 62K 长上下文 | 换入换出 | 车道专家 |
|---|---:|---:|---:|---:|
| 无 | **25.95 / 25.95** | 17.62 | 716–728 | 9.0–9.3% |
| 短上下文 trace 造的 | **26.48 (+2.0%)** | — | 305 | 5.0% |
| 62K trace 造的（round 1 上线的那份） | **24.49 (−5.6%)** | **17.99 (+2.1%)** | — | — |
| 两份计数相加（merged） | 24.37 (−6.1%) | — | 523 | 14.2% |
| 两份按排名交叉（interleaved） | 23.15 (−10.8%) | — | 792 | 18.3% |

覆盖率不是解释（merged 覆盖短上下文 91.3% 却更慢）。真因是 **`l.heat` 用 profile 计数初始化、直接驱动
换入换出策略**：稀释过的 profile 让缓存来回抖（500–800 次换入 vs 匹配时的 305 次），越「兼顾」越差。

**决定：生产配置回退成不带 `--expert-profile`**（短/长都中性），`profile.bin` 留在包里作为「只跑长上下文
的服务器」的可选项，注释写清它只对长上下文 +2%。

## 14. 本轮净结果

- 仪表（主机时间/GPU 事件对照）已加，下一次编译前它是判断「该减派发还是该改内核」的唯一依据。

## 15. 测量环境本身是最大的噪声源（本轮最大的意外）

同一二进制、同一配置、同一 prompt，解码在 **8.7 / 10.3 / 25.3 / 25.6 tok/s** 之间跳。差别不在代码，在
**118 GB 专家包的 page cache 是否还在**：

| 状态 | 解码 | 车道每个专家的成本 |
|---|---:|---|
| 暖（包在 page cache 里） | 25.3–25.9 tok/s（39 ms/token） | prep 0.03–0.05 ms，读命中 |
| 冷（刚被别的实验冲掉） | 8.7–10.3 tok/s（96–115 ms/token） | 读盘，每 token 多 60–75 ms |

任何 A/B **必须先跑一次暖机**，否则会得出完全相反的结论（本轮第一次测 `DS4_MOE_TOKEN=0` 时它「更慢」，
其实两次都在冷态）。上一轮九次诊断全落空，很可能一半是这个原因。

生产上的推论：**服务保持常驻（别让它卸载）、别在同一台机器上跑会吃掉 100 GB 内存的东西**，
暖态 25.6 tok/s、冷态 8.7 tok/s 是同一个配置。

## 16. 本轮否掉的又一条：`DS4_MOE_TOKEN=0`

T=1 的专家走 `win_experts`（窗口内核）而不是 `moe_gate_up`/`moe_down`（token 内核）。暖态对照：

| 配置 | 解码 | 车道专家 |
|---|---:|---:|
| 默认（token 内核） | **25.65 tok/s** | 5217/45840 (11.4%) |
| `DS4_MOE_TOKEN=0`（窗口内核） | 6.86 / 7.33 tok/s | 5882 / 5520 |

**慢 3.5 倍**，否决。token 专家内核是对的。

## 17. 现在的位置（把账合起来看）

- 墙钟 38.4 ms = GPU 37.3 ms（计算 ~32 + 自旋等车道 ~5）+ 0.9 ms 空隙；主机层内 32 ms ≈ GPU 计算 32 ms。
- 32 ms 的 GPU 计算里，按字节算全都远低于带宽（例：6 个专家的 gate/up 共 ~34 MB，实测 5.17 ms ≈ 6.6 GB/s，
  比显存带宽低两个数量级）→ **m=1 的小内核是延迟/占用率受限，不是带宽受限**。
- 因此剩下的每一条路都要么改内核（提占用率、融合、prefetch），要么改架构（一次喂多 token）。
  前者是纯内核工程，后者已被 MTP 窗口路径的天花板（24.9 tok/s）堵住。
- 便宜的旋钮已经全部试完并关闭：PCIe 双通道、`DS4_AHEAD`、`--mmap-experts off`、`--ssd-cache`、
  `DS4_HEAT_BUDGET`、`DS4_MOE_TOKEN=0`、profile 的各种变体。

## 19. 本轮收口

便宜的旋钮到此全部试完（见 §11/§14/§16/§18 的否决清单）。剩下的每一条都是内核工程：

1. **m=1 内核的占用率/延迟**：GPU 32 ms 计算里每一格都远低于带宽（例：6 专家 gate/up 34 MB / 5.17 ms = 6.6 GB/s），
   是延迟受限。要动 `gg::mv` / `x3::moe_*` 的 tiling、prefetch、寄存器压力。
2. **派发数**：主机 32 ms 对应 ~800 次派发/token（40 层 × ~20），每次 ~40 µs。融合能同时降主机和 GPU 的空转，
   但 native IQ pack 没有图捕获（`generate.cpp:5502` 明确排除），只能手写融合内核。
3. 两者必须同时降——单动一边已经被 §12 的测量证明是零收益。

## 20. 决定性的一刀：路由专家只占解码的 ~13%

把 `--experts` 从 6 降到 3、再降到 1（暖态，同一协议，192 token），看解码掉多少：

| experts | 解码 | ms/token | gate/up | down+post | cpu-lane 自旋 |
|---:|---:|---:|---:|---:|---:|
| 6 | 25.32 tok/s | 38.7 | 5.17 | 5.17 | 6.31 |
| 3 | 27.68 tok/s | 35.3 | 3.11 | 4.09 | 3.62 |
| 1 | 28.36 tok/s | 34.4 | 1.60 | 4.55 | 2.91 |

**把每 token 的专家从 6 个砍到 1 个，解码只从 25.3 涨到 28.4（+12%）。**
也就是说：前四轮追的「专家放置 / PCIe 搬运 / 车道」这一整条线，天花板是这 ~13%；
`--experts 1` 剩下的 34.4 ms 才是大盘。

## 21. 大盘是什么：稠密权重（每 token 6.2 GB）

`--pack-info` 的账：专家 132.1 GB @1.94 bpw（544 G 参数），**稠密 209.26 GB**，
其中 **engram 202.97 GB**（只在第 1、14 层，按行读，行缓存 720 行），非 engram 稠密 = 6.29 GB。

引擎启动时也自报 `weights 6.20 GB` 常驻显存 —— **这 6.2 GB 是每个 token 都要全读一遍的**，
对比专家的 2.06 GB/token，稠密是专家的 3 倍。按 stage 表核对：

| stage | ms/token | 对应字节 |
|---|---:|---|
| attn proj (norm+q_a/kv) | 6.9 | 稠密 |
| attn tail (o_fin+wo) | 6.4 | 稠密 |
| routing + shared | 5.5–6.3 | 稠密（shared expert） |
| sparse attn + comp/idx | 2.5 | KV |
| 专家 gate/up + down | ~10 | 2.06 GB 专家 |

稠密那几格合计 ~21 ms ≈ 6.2 GB / 300 GB/s，**已经贴着带宽跑**（卡上约 450–500 GB/s）。
所以「把内核写快点」对它们没用——**只能减少字节**。

## 22. 因此唯一还能大改的一条：稠密权重降精度（现成工具，需拍板）

仓库里有 `tools/dsv41/dense_requant.py`：把 attention / compressor / indexer / shared experts 重新量化成
Q4_K / Q5_K / Q6_K / Q8_0，写成旁边一个 `dense.bin` 覆盖层（专家、Engram、embedding/head 都不动），
再用 `pack_gguf.py --dense-override DIR` 接上。当前这些张量是 BF16/F32/F8_E4M3/Q5_K/Q6_K/Q8_0 的混合。

估算：非 engram 稠密 6.2 GB、平均约 6.5 bpw → 换 Q4_K（4.5 bpw）约 **4.3 GB**，
那 ~21 ms 的稠密阶段 → ~15 ms，**token 38.7 → ~32 ms，解码 25.3 → ~30 tok/s（+20%）**。
代价是 attention/shared expert 的精度（Q4_K 对这两处通常是安全档，但要跑 `tools/dsv41/iq_bench.py` 的 24 题
精度基准对比，且这是**用户可感知的质量取舍**，不是纯性能开关）。

**下一步需要用户拍板**：要不要做这个覆盖层（约 20–30 分钟生成 + 一次精度基准）。
如果不做，解码在这套 1.94 bpw 专家 + 6.5 bpw 稠密的格式下，天花板就在 ~28–30 tok/s 附近。

### 22.1 实测：`dense_requant.py` 在这份 pack 上几乎没料可动

跑了 `tools/dsv41/dense_requant.py --type Q5_K`（用 numpy 的 venv + LM Studio 的 libggml-base.so）：

```
dense Q5_K: 19 tensors, 0.12 GB BF16 -> 0.04 GB, 0 s
```

**只找到 0.12 GB 的 BF16 张量**（compressor / indexer 那些小矩阵）。主 attention（wq_a / wq_b / wkv / wo_*）
和 shared experts 在这份 pack 里**已经是量化过的**（F8_E4M3 / Q5_K / Q6_K / Q8_0 的混合，见 `--pack-info` 的
`dense types:` 一行），不是工具期望的 BF16 源。

所以要动稠密权重，得**新写一条 fp8/Q8_0 → Q5_K 的重量化路径**（先把源解到 f32 再喂 `ggml_quantize_chunk`），
按 8→5.5 bpw 估：6.2 GB 稠密约 → 4.3 GB，那 ~21 ms 的稠密阶段 → ~15 ms，**token 38.7 → ~32 ms，
解码 25.3 → ~30 tok/s（+20%）**。代价是 attention 的精度（可先跑 `iq_bench.py` 24 题对照）。
**这是模型精度取舍，不是性能开关，需要用户拍板。**

## 23. 结论：这套格式下解码的天花板

| 项 | 现状 | 说明 |
|---|---|---|
| 解码 | 25.3–25.9 tok/s（暖，短上下文）；17.6–18.0（62K） | 冷态 8.7–10.3 |
| 路由专家（可优化上限） | ~13% | `--experts 1` 只到 28.4 tok/s |
| 稠密权重 | 6.2 GB/token，~21 ms，已贴带宽（~300 GB/s） | 只能减字节 |
| 主机侧 | 32 ms ≈ GPU 计算 32 ms | 单动一边无效 |

要继续往上，只有三条，都超出「调参」范围：
1. **稠密权重降精度**（fp8/Q8_0 → Q5_K）：+20% 量级，需要新工具 + 精度基准 + 用户拍板。
2. **m=1 内核工程**（融合 / 占用率 / prefetch）：主机与 GPU 必须同时降。
3. **一次喂多 token**（MTP 窗口）：已有实测天花板 24.9 tok/s，等于白干。

## 24. MTP（DSpark）实测：现在比不开慢 20%，但结构是对的

用户指出「MTP 才是大头」。本机确实有两份带 drafter 的 pack（`dsv41-iq2xxs-pack-mtp` 8.5 GB、`-mtp2` 4.92 GB，
block_size 5、markov_rank 256、1245 个 MTP 张量）。暖态、192 token、同一协议：

| 配置 | 解码 | 车道专家 |
|---|---:|---:|
| pack-mtp2，`--dspark off`（对照） | **23.18 tok/s** | 7975/45840 (17%) |
| pack-mtp2，`--dspark on` | 18.18 / **18.74** tok/s | 17340/47325 (37%) |

**接受率是满分**：`33 rounds | offered 158, accepted 158 (100.0%) | 5.82 tokens a round` —— 草稿质量没问题。

### 24.1 一轮 304 ms 花在哪（引擎自报）

| 项 | ms/round | 折成 ms/token |
|---|---:|---:|
| verify（层内） | 293.0 | 50.3 |
| 　其中 CPU 车道 | 86（14.8×5.82） | 14.8 |
| 　其中**主机发射**（"the rest host launches"） | ~205 | **35.3** |
| mv 派发（286 calls/window） | 11.6 | 2.0 |
| 草稿 draft | 7.1 | 1.2 |
| rest（层外） | 11.1 | 1.9 |

**关键：单 token 路径的整层主机时间才 32 ms，而 T=6 窗口一轮 293 ms —— 一次 6 token 的层遍历，主机侧花了
单 token 的 9 倍。** 稠密权重确实被摊薄了（每 token 的稠密从 21 ms 降到约 5 ms，这才是 MTP 的理论收益），
但被窗口路径的主机发射开销整个吃掉了。

### 24.2 因此 MTP 要赢，只需要修一件事

窗口路径的主机侧每层要做 gather rows / plan / 一堆小内核（286 次 mv 调用/窗口 + 每层的其它派发），
**把 293 ms 压到 100 ms 以内，MTP 就是 5.82 token / 110 ms ≈ 53 tok/s**，是基线的 2.3 倍。
车道那 86 ms/轮是第二刀（窗口里 6 个 token 的专家并集更散，37% 落车道），修好第一刀后再看它。

这条和 §17 的结论一致：**这台机器上解码的敌人始终是「每层十几个小内核 + 主机发射」**，
只是 MTP 把同一个敌人的赌注放大了 6 倍。下一轮就攻这个：先把窗口路径每层的派发数打出来
（`mv` 已有计数，再补 attention/norm 侧），然后合内核。

## 25. MTP 窗口路径的主机时间：找到了「每层一次同步」

### 25.1 先修好仪表：`DS4_TLOG` 在 SYCL 构建上是死的

`ds4_dbg()` 在非 Metal 构建里是 `constexpr false`（`ds4_launch.h:242`），所以 `DS4_TLOG`（主机侧分相计时）
从来没生效过。改成 `std::getenv("DS4_TLOG") != nullptr` 后它活了（一行改动，不影响默认行为）。
MTP 一轮（T=6）的主机分相：

| 相位 | ms/轮 | 说明 |
|---|---:|---|
| attn（层首→注意力结束） | ~5 | |
| moe_pre（→路由+shared 结束） | ~9 | |
| down+post（→本层结束） | **~300** | 几乎等于整轮 304 ms |

主机在最后一段里**不是在派发，而是在等**（否则一段只该十几毫秒）。

### 25.2 第一个假设（否决）：`h_part` 的每层 H2D 拷贝

窗口路径每层 `s->memcpy(d.cpu_part, h_part, T*D*4)` 把 CPU 车道的结果拷进显存。`h_part` 本来就是
`sycl::malloc_host`（USM host，设备可直接读，token 路径就是直接传主机指针的），所以怀疑这个 in-order 队列上的
阻塞拷贝在排空队列。改成直接传 `h_part` 实测：

| 配置 | 解码 |
|---|---:|
| 直接传主机指针 | 18.95 / 18.87 tok/s |
| 保留拷贝（原样） | 18.81 tok/s |

**无差别**，而且 `--dump-logits` 两次的 md5 不同（设备读 USM host 在这条路径上不一致）→ **改动已回退**，
源码回到原样，只留下可 A/B 的开关想法（未保留）。

### 25.3 真正的同步点：每层两次阻塞 D2H

`ds4_model.dp.cpp:13012 / 13016`，每层紧跟路由之后：

```cpp
s->memcpy(h_w, d.rw, T * kPicks * 4);   // 路由权重 -> 主机
s->memcpy(h_x, d.x,  T * D * 4);        // FFN 输入 -> 主机（T=6 时 123 KB）
dpct::sync_barrier(d.ev, s);
```

in-order 队列上的 D2H 拷贝必须等前面所有内核（本层注意力 + 路由）跑完，**主机因此每层被钉住一次**：
40 层 × 约 5 ms ≈ **200 ms/轮**，正好是 §25.1 里那段 300 ms 的绝大部分（剩下 ~86 ms 是 CPU 车道本身）。

token 路径没有这个问题：它用 mailbox 让设备把 x 写进请求槽，服务线程自己取，主机从不阻塞。

### 25.4 下一轮的做法（已明确）

把这两次 D2H 从计算队列上摘下来：路由内核完成后在**独立拷贝队列**上发 D2H（用事件只依赖路由内核），
主机等那个事件而不是等整个队列；同时把 shared expert + 驻留专家的 gate/up 先排进计算队列，
让 GPU 在主机算车道专家的那 2–3 ms 里继续干活。
预期：把 200 ms/轮的主机阻塞压到接近 0 → 304 → ~110 ms/轮 → **40–50 tok/s**。

## 26. MTP 窗口的主机侧：每层 7 ms，而 T=1 只要 0.9 ms

加了 `tmark`（`DS4_TLOG` 下的主机分相标记，插在 async 路径的 route / shared / gate-up / down / 层尾）。
同一二进制、同一 pack、只差 `--dspark`：

| 段（主机） | T=1（dspark off） | T=6（MTP 窗口） |
|---|---:|---:|
| 层首 → shared-down 之前（注意力+路由+shared gate/up） | **0.91 ms** | **7.06 ms** |
| shared-down → gate/up 提交 | 0.04 | 0.00 |
| gate/up → 车道等待 | 0.04 | 0.00 |
| 其余 → 层尾 | 0.09 | 0.20 |
| 合计/层 | ~1.1 ms | ~7.3 ms |

40 层 × 7.3 ms = **292 ms/轮**，正好是实测的 304 ms/轮 —— **窗口路径的墙钟就是这条主机串行链**，
GPU 的 155 ms 计算全部藏在这些等待里。

### 26.1 排除过的解释

- 车道线程抢核：`STRATA_DS4_LANE_FREE=2 / 8 / 12` → 19.27 / 19.17 / 18.93 tok/s，**无差别**（7.0–7.1 ms/层）。
- 两段式专家内核：`DS4_EXP_2PHASE=0` vs `1` → 19.09 vs 19.11 tok/s，无差别。
- `DS4_WIN_HOSTWAIT=1`（窗口里改成主机侧等车道标志）→ 18.90，无差别。
- 上一轮的 `h_part` H2D 拷贝（§25.2）→ 无差别且 logits 不一致，已回退。

### 26.2 下一步（一轮可完成）

那 7.06 ms 还在「注意力 + 路由 + shared gate/up」这一整段里，需要在同一段再插 3 个标记（注意力结束 / 路由发布结束 /
shared gate-up 提交结束）把它切成三段，然后针对命中的那一段去掉主机等待（最可能是注意力之后某处的隐式同步）。
切完就能知道该动 `route_publish`、`hc_pre_norm` 还是 `mv` 的哪一处。

## 27. 切开了：那 7 ms 全在「注意力」一段，而且随窗口 token 数线性涨

把 §26 的 7.06 ms 段再插 3 个标记（注意力结束 / 路由发布 / shared gate-up 提交）后：

| 段（主机/层） | T=1 | T=4（`--dspark-block 3`） | T=5（默认 block 5） |
|---|---:|---:|---:|
| **注意力** | 0.9 | **5.87** | **7.02** |
| 路由 | 0.02 | 0.02 | 0.02 |
| shared gate/up | 0.09 | 0.10 | 0.10 |
| shared down / gate-up 提交 | 0.04 | 0.00 | 0.00 |
| 其余 | 0.09 | 0.21 | 0.20 |
| 一轮 | — | 256 ms / 3.92 tok | 305 ms / 5.84 tok |

- 注意力那段随 T 近似线性涨（每多一个 token 约 +1.2 ms/层），而 T=1 只要 0.9 ms/层。
  也就是说**窗口里每个 token 的注意力要 ~1.6 ms/层，比单 token 的 0.9 ms 还贵 1.8 倍**。
- 40 层 × 7 ms = 280 ms/轮，就是整轮。GPU 的专家计算藏在这段等待里。

### 27.1 MTP 输在哪：三笔账

| 项 | 6 个单 token | 一个 T=5 窗口 | 差 |
|---|---:|---:|---:|
| 稠密权重（可摊薄） | 6 × 21 = 126 ms | ~29 ms | **−97 ms** |
| 注意力 | 6 × 0.9 × 40 ≈ 36 ms/token | ~48 ms/token | **+12/token** |
| 专家 MoE | ~10 ms/token | ~21 ms/token | **+11/token** |
| CPU 车道 | ~6 ms/token | ~15 ms/token | **+9/token** |

MTP 的收益（稠密摊薄 −97 ms/轮）被「窗口路径每 token 的注意力 +12、MoE +11、车道 +9」吃掉，
净结果是 −20%。**这不是靠调参或去掉某个同步能翻过来的**：窗口路径的注意力与 MoE 内核在 T>1 时
每个 token 都比 T=1 贵 1.8–2 倍，要赢必须把那两个内核的 per-token 效率做到与 T=1 持平或更好。

### 27.2 目前最好的 MTP 配置

`--dspark-block 5`（T=5，5.84 token/轮，接受率 100%）= **19.1 tok/s**，仍低于不开 MTP 的 23.2。
T=4 更差（15.1 tok/s，3.92 token/轮）。所以现状是「MTP 开着但不用」是对的。
