# 明早怎么验（2026-11-03）

> 一页纸。分析细节在 [EXPERT_KERNEL_ALU.md](EXPERT_KERNEL_ALU.md)，这里只讲**做什么、看什么、怎么决定**。

## 一条命令

```bash
cd /data/strata-new && tools/overnight/morning.sh
```

它会：查服务是否停着 → 拿 GPU 独占锁 → 跑 4 步 → 输出存 `/tmp/morning-<时间戳>/` → 最后打印汇总。
全程不动生产配置（`tc_ab.sh` 临时改、退出时无条件还原）。想跳过最慢的端到端 A/B：`morning.sh fast`。

## 五步分别回答什么

| 步 | 命令（脚本里已含） | 回答的问题 | 看哪一行 |
|---|---|---|---|
| 1 | `iq_dequant_bench 131072 20 4 80 128` | 解量化本体多快？瓦片构建多贵？BM 调大值多少？ | `GPU deq8` / `GPU deq8v` / `tile BM…` / `隐含 TFLOPS` |
| 2 | `xmx_gemm_bench 16 both 30 sweep real` | 融合 vs 两段式，在哪个 rows/expert 交叉？ | `2ph/fus` 列（>1 表示两段式更快） |
| 3 | `ds4_iq_test_tc`（`NO_TC=1` vs `TC=1`） | **张量核到底对不对、快不快** | `worst … tol … ok/FAIL` 与 `--bench-tiles` 的 us/吞吐 |
| 4 | `DS4_EXP_2PHASE=1 ds4_iq_test_tc` | **两段式的数值对不对**（代码已写好，默认关） | `set gate_up` / `set down` 的 `worst` 与第 3 步的 `3a` 比 |
| 5 | `tc_ab.sh bench/prompts/p45k.txt 48` | 整机端到端值多少 | 三组的 `prefill tok/s` + 输出开头 90 字符 |

## 判读顺序（先看钱最多的那一笔）

> **优先级在 11-02 夜里被重排过**：既有实验（`DSV41_SYCL_PORT.md:475-490`）证明"换内积单元"只值 1%，
> 而 oneMKL 在引擎自己的形状上是 **94.9 TFLOPS**（不是 9）。所以**两段式是 5–9×，张量核最多 1.2×**。

1. **第 2 步，M=900 那行的 `2ph/fus`** ← 最值钱的一笔。预测 **5–9×**（解量化从 15 遍降到 1 遍，
   GEMM 走 oneMKL 95 TFLOPS）。≥2 就值得把预填充改成两段式（`prefill.cpp:4364` 已有现成调用）。
2. **第 1 步，`tile BM=128` vs `BM=64`**：预测 **1.88×**（重复解量化 15 遍 → 8 遍）。
   只需改一个 `constexpr`（`ds4_iq.dp.cpp:1000`），可以和两段式叠加。
3. **第 1 步，`GPU deq8` 的 Gval/s**：验证"反推 D ≈ 35（gate+up）/ 50（down）Gval/s"这条因果链。
   落在 30–60 就是印证；`deq8` 与 `deq8v` 打平说明解量化写法不是变量（与 10-30 的三种内积 ±1% 一致）。
4. **第 3 步，张量核对拍**：先看正确性（`worst … tol … ok/FAIL`），再看 `--bench-tiles` 的吞吐。
   **期望值已经调低**——内积单元换掉只值 1% 是既有实测，它可能的额外好处是"把 ALU 槽位让给解量化"，
   只有上卡才知道。出 FAIL 就先隔离是 gate/up 还是 down：

   ```bash
   STRATA_DS4_TC=1 STRATA_DS4_TC_ONLY=gu   build-sycl-tc2/ds4_iq_test_tc
   STRATA_DS4_TC=1 STRATA_DS4_TC_ONLY=down build-sycl-tc2/ds4_iq_test_tc
   ```

5. **第 4 步，端到端**：只是确认。122k 上单次能差 ±36%，至少 3 轮或只看阶段表 ms。

## 结论对应的动作

| 结果 | 动作 |
|---|---|
| 第 2 步 `2ph/fus` ≥2 | **两段式的代码已经写好了**（默认关）：`STRATA_DS4_NO_TC=1 DS4_EXP_2PHASE=1 build-sycl-tc2/ds4_iq_test_tc` 先验数值，再端到端。细节见 [TWOPHASE_EXPERTS_DESIGN.md](TWOPHASE_EXPERTS_DESIGN.md) 第七节；`tile BM=128` 若也高，一起改 |
| 第 2 步 <1.2 | 两段式在这张卡上没优势 → 回到 BM 与 TC 两条 |
| 第 1 步 `BM=128` ≥1.5× | `ds4_iq.dp.cpp:1000` 的 `constexpr int BM = 64` → 128，重编验吞吐 |
| 第 3 步 TC 对拍通过且 ≥1.2× | `tools/overnight/tc_promote.sh promote [minrows]`，再 `START.sh start` |
| 第 3 步 TC 对拍 FAIL / 崩 | 先 `TC_ONLY=gu/down` 隔离；坏的那半关掉，好的那半照样能落地 |
| 想随时撤回 | `tools/overnight/tc_promote.sh revert`（只改回配置，二进制从不被覆盖） |

## 数字量级参考（对不上就是环境变了，先别解读结论）

| 指标 | 今天的参考值 | 离谱的样子 |
|---|---|---|
| CPU 标量解量化 | 1.2–1.3 Gval/s | >3 或 <0.5 都说明机器在忙别的事 |
| GPU `deq8` | 判据线 33 Gval/s（=4.2 TFLOPS）；合理区间 30–300 | <10 → GPU 没跑满或时钟掉了 |
| `tile` 相对 `deq8` | 应 ≤1（多了一次 f16 转换和 SLM 写） | 远大于 1 → 说明 barrier/存写是瓶颈 |
| oneMKL f16 GEMM | M=96 时 ~9；引擎自己的形状（M≈8000）**94.9** | M=900 掉到 <20 要知道是在预期内（小 M 效率低），掉到 <5 → MKL 没走上 |
| F32 专家内核 | gate/up 4.2、down 6.0 TFLOPS | 这两个数今天是从阶段表读的 |
| 45k / 122k 预填充 | 347 / 270 tok/s（±36% 噪声） | 差一倍先查是不是混入了别的负载 |

## 三条纪律

- 一次只跑一个引擎；脚本会先拿 `tools/overnight/gpu_lock.sh`。
- 崩了/`DEVICE_LOST` 立刻停手，别重启机器（重启可能挂驱动）。
- 第 3 步是纯内核测试，**不需要启动服务**，所以就算 TC 有问题也污染不到生产。
