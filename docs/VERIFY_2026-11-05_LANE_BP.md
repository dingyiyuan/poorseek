# LANE_BP 修复的收尾验证（2026-11-05 夜）

修复本身：`85d8f4a3` 路由邮箱背压 `DS4_LANE_BP`（默认开），病态复现已见
`7e05e67b` / `ad46d128`（`--cpu-threads 1` + `BP=0` 时每请求必死锁；`BP=1` 时跑完）。
本文件补的是**病态夹具之外**的两项收尾：长会话速率下限、以及正确性口径。

结论：**24 个请求零掉崖、零 STALL，解码率全程平坦；24 题准确率 24/24（此前基线 19/24）。**
「>15 tok/s」这条判据是擦边（中位 14.9），但它是**绝对值**判据，不是退化判据——退化判据（前后半段
对比）完全达标。

## 1. 长会话速率：24 请求 × 128 token（与交接口径一致）

命令（注意必须先 source oneAPI，见 §5）：

```bash
source /opt/intel/oneapi/setvars.sh --force
cd /data/strata-new
R3_NQ=24 R3_MAXTOK=128 R3_TIMEOUT=150 R3_DSPARK=off \
  /usr/bin/python3 tools/dsv41/slow/repro.py 1.0 bp24
```

| 指标 | 实测 |
|---|---|
| 请求数 / 完成数 | 24 / **24**（0 STALL，0 timeout） |
| 解码率 | **12.47 – 18.03 tok/s**，中位 **14.93**，均值 15.24 |
| 前后半段 | 前 12 个中位 **15.17**，后 12 个中位 **14.85** → 无衰减 |
| `down+post` | 0.33 ms/层（首个 0.63，之后稳定 0.33–0.35） |
| swaps | **全程 0**（专家环未发生一次换入换出） |
| 对照组（病态） | 0.15 tok/s，`down+post` 101 ms/层，swaps 冻结 |

判读：
- **掉崖没有了**：24 个请求里没有一个掉到 1 tok/s 以下，也没有一个超时。修复前同一夹具在第 2–6 个
  请求就全部 STALL。
- 每请求只生成 **47 token**（模型自己收尾），固定开销（预填充 + 起跑）占比很大，所以
  「>15 tok/s」这条**绝对值**判据只是擦边；真正的退化判据（后 12 个 vs 前 12 个）是平的。

| 指标 | 实测 |
|---|---|

| 解码率 | **13.15 – 24.59 tok/s**，中位 **17.09**，均值 17.34 |

生成长度 30–260 token（多数 239），所以这一轮同时覆盖了「短回答」和「240 token 长回答」两种形态。

## 3. 长会话浸泡：60 请求 × 128 token（远超历史崩点）

历史崩点是「十几到二十几个请求」之后开始掉到 0.15 tok/s，所以 24 个只是**擦着崩点**。
再往上推到 60 个：

| 指标 | 实测 |
|---|---|
| 请求数 / 完成数 | 60 / **60**（0 STALL，0 timeout） |
| 解码率 | **12.38 – 19.33 tok/s**，中位 **15.20**，均值 15.44 |
| 分段中位 | 前 10 个 16.01 → 中段 10 个 16.54 → 末 10 个 **13.71** |
| `down+post` | **0.33 ms/层，全程一动不动**（首次 0.63，之后恒定） |
| swaps | **全程 0** |
| 低于 10 tok/s 的请求 | **0 个** |

判读：60 个请求、约 9 分钟连续解码，**没有一次塌方**。末段中位比前段低约 14%，
但那是软性的（`down+post` 与 swaps 完全没变），和原来「0.15 tok/s、down+post 101 ms/层、
swaps 冻结」是两种完全不同的形态——**原来的掉崖在 60 请求尺度上不复现**。

## 4. 正确性口径：24 题准确率

```bash
# prod 引擎（pack-real, --dspark off, --vram-experts 1.0）
/usr/bin/python3 /tmp/acc/iq_bench_auth.py --api http://127.0.0.1:8160 \
  --tag bprefix --out /tmp/acc/bprefix.json
```

结果 **24/24**（数学 10/10、逻辑 7/7、计数 7/7）。此前记录基线 **19/24**。

注意口径：这不是严格 A/B（基线那轮与本次的 pack/放置/config 不完全相同），只能读作
「没有准确率回归，且这轮全对」。若要当 A/B 引用，需在**同 pack、同放置（`--profile-readonly`）**
下把 BP=0/BP=1 各跑一次 24 题。

## 5. 两个会浪费一整晚的坑（记录在案）

1. **`repro.py` 必须带 oneAPI 环境**。它直接 `/usr/bin/python3 -m serve.server` 起引擎，
   不经过 systemd unit 的 `source .../setvars.sh`，于是：
   `build-sycl-jit/strata-dsv41: error while loading shared libraries: libmkl_sycl_blas.so.6`
   （server 反复重试，exit 127）→ 客户端看到的是**每个请求都 STALL、swaps 0**，
   和死锁复发的表象一模一样。第一次跑就踩了这个坑，浪费了 4 个 120 s 超时。
2. **`repro.py` 会 `systemctl --user stop dsv41.service`**，且结束时只 SIGTERM 自己的 pm 组。
   每轮跑完必须手动 `systemctl --user start dsv41.service`，否则 prod 引擎是停的。
3. `tools/dsv41/iq_bench.py` 的 `ask()` **不带 Authorization 头**，打 prod（8160 有 api_key）
   会秒 401 → 打印 0/24（每题 0 s）。用 /tmp 副本加 `Authorization: Bearer <key>` 即可，
   不要因此误判「模型全错」。

## 6. 遗留风险（未处理，与本次修复无关）

`--vram-experts 1.0` 在 32 GB 卡上只剩 ~595 MiB 空闲（`docs/MTP_HANDOVER_2026-11-04.md` §8）。
本机只要多几百 MB 的显存占用就可能把引擎推回 0.15 tok/s。建议部署前改 0.5–0.75
（历史实测：0.5 时 24 题全程 14–22 tok/s，速度与 1.0 健康态持平）。
本轮两次实测都是 1.0，且 swaps 全程 0——说明只要显存不被打穿，1.0 本身能跑。

## 7. 一句话

**背压修复在真实长会话负载下成立：24 个请求不掉速、不超时、无 swap 抖动；再推到 60 个请求仍然零 STALL；24 题全对。**
下一步该动的不是这里，而是 §6 的显存余量与交接文档 §3 的 PCIe 双通道方向。
