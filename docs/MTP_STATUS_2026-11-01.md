## 二十一（20:55）：验证窗口的一半时间 GPU 在空转

`prof_mark` 记的是 **GPU 事件**（`get_profiling_info` 的 command_end 差），所以"事件合计"= GPU 真正在跑的时间；与墙钟的差 = **GPU 空闲**。

| 场景 | 墙钟 | GPU 执行 | GPU 忙 |
|---|---|---|---|
| 单 token 解码（T=1） | 36.2 ms | 36.2 ms | **~100%** |
| 验证窗口（T=6，`pack-mtp2`） | **306.9 ms** | **155.1 ms** | **50%** |

窗口的 306.9 ms 拆解：
- GPU 执行 **155.1 ms**（其中 `down+post` 一格 126.1 ms，因为 T>1 路径不打 gate/up 与 cpu-lane 标记，整个 MoE 都算在这里）
- CPU lane（主机算专家）**76.3 ms**
- **纯发射/同步空档 ≈ 75 ms（24%）**——既不是 GPU 计算，也不是 CPU lane

对比 `--experts 1`（每层只有 6 专家、MoE≈0）：verify 167.6 ms、事件合计仅 86.6 ms → **GPU 忙 52%**，且 `down+post` 仍有 59.9 ms（1.5 ms/层），说明这一格里**不全是专家计算**。

### 结论
**MTP 的验证窗口不是"算得慢"，而是"一半时间在等发射/同步"。** 这与 XTier 的做法正好相反：他们用 CUDA graph 捕获把每步的发射开销压到一个；我们是 40 层 × 每层 5–10 个小内核串行发射，GPU 有一半时间没活干。

### 这解释了之前所有的反常
- 为什么 verify 与 T 几乎无关（262/290/306）：**固定的是发射次数，不是计算量**；
- 为什么每层 6.5–7.5 ms 而单 token 是 0.95 ms：同样 40 层，窗口路径每层多出几倍的发射与同步；
- 为什么把专家数从 36 降到 6 只省 40%（285→167）：**省的是计算，剩余的固定发射开销不动**。

### 下一步（唯一值得做的方向）
把窗口路径的**每层发射次数打出来**（在 `mv()`/`finish()` 处计数），确认 75 ms 对应多少次发射；若确认是发射主导，就合并 kernel 或减少每层的提交段数——这是把 21 → 28 tok/s 的唯一路径。

## 二十二（21:30）：MTP 窗口的优化空间已到顶 —— 即使全修好也只是"追平"

### 本轮排除的三个假设
| 假设 | 测量 | 结论 |
|---|---|---|
| 每窗口发射次数太多 | **278.9 次派发/窗口**，但主机只在派发里花 **10.6 ms** | ✗ |
| 内核里自旋等 CPU 车道（`wa.wait_ptr`） | 改成主机侧等待（`DS4_WIN_HOSTWAIT=1`）后实测 **winwait = 0.0 ms**——答案早就就绪 | ✗（附带 +1.3%：19.39 → 19.64 tok/s，因为省掉每内核的自旋检查） |
| 每层有隐式 `wait()` | 层路径里没有任何 `->wait()`（只有 `STRATA_METAL` 条件 flush） | ✗ |

缺口特征：**~65 ms/窗口、约 1.6 ms/层，且与专家数无关**（experts=1 时 64 ms，experts=6 时 69 ms）。

### 决定性的一笔账
| 情形 | verify | 吞吐 |
|---|---|---|
| 现状 | 300 ms | 21.1 tok/s（暖 bench） |
| 缺口全部省掉 | 235 ms | **24.9 tok/s** |
| 连 GPU 事件外的一半也全解释掉 | 160 ms | 36.5 tok/s（不现实） |

**关键：把那 65 ms 完整消掉，也只是 24.9 tok/s ≈ 基线 24.5**——等于白忙。

### 结论
MTP 这条线到此为止。继续挖那 65 ms 的最好结果是"追平不开 MTP"，而这 65 ms 还涉及事件覆盖与主机侧零碎操作，属高成本低回报。

### 真正的杠杆（按有效性）
1. **显存容量**（硬件）——专家命中率从 10% 提高才是 2× 级的改动；
2. **主机内存带宽**（已到 38 GB/s vs 实测 49–51.6），无余量；
3. **每层小内核合并**：真实负载里 `routing+shared` 7.89 ms 而权重只需 0.08 ms，这是唯一还有确定收益的软件项（约 5%）。

## 二十三（22:35）：DeepInfer 精读结论 + 两次失败的 A/B + 方法论修正

### DeepInfer（子智能体报告 `docs/deepinfer-report-for-strata.md`）纠正了我们三处判断
1. **"预取下一层专家"不可行**：层 N 的专家 id 依赖层 N 的 attention 输出（h→attn→gate→topk），依赖链上无提前量；框架自己也没有任何层间专家预取。**此前"预取是藏车道延迟的唯一办法"作废。**
2. **提交粒度不是空转的原因，同步点才是**：他们一步 decode = 1 次 graph replay + 1 次草稿 + 5–6 个采样 kernel，并用 `forbid_cuda_sync()` 把"每步最多一次同步"做成硬约束。与我们的实测一致（279 次派发仅 10.6 ms 主机时间）。
3. **截断验证对我们不生效**：他们的摊销来自权重全驻留；我们 k=3 时 262 ms、k=6 时 285 ms，成本几乎不随 k 变，47.5 ms/token ≈ 单 token 45 ms（摊销率≈0）。

### 可搬的四条（按我们自己的数据重排）
| 项 | 依据 | 判断 |
|---|---|---|
| 层内填充（发完专家请求立刻算 shared expert + norm/rope/store） | `mlp.py:601-609` | **最该做**，直接治 22 ms 车道等待；但只有 shared expert 能重叠 |
| 加深 DMA 队列（一层一票据 + 32 深 + 设备端完成位图） | 自有 hotpin 数据 4/16/32 队列 = 23.5/30.5/35.0 GB/s | 有潜力，但下面的 A/B 没测出 |
| 同步审计（每步设备端等待次数 == 层数 40） | `utils.py:119-132` | 便宜，先做 |
| 验证窗口内按 expert 去重 | — | 只服务 MTP，跳过 |

### 实测：`DS4_CACHE_INFLIGHT` 8 → 32 **没有可分辨收益**
| 配置 | 短-中文 | 长-512 | 中-256 |
|---|---|---|---|
| 默认 8 | 19.5 | 23.2 | 20.5 |

已回退。

### 方法论修正（重要）
**同一配置的两轮之间，单 prompt 的方差可达 4.6 tok/s（18.5 vs 23.1）**。这意味着：
- 我之前所有"1 轮/配置"的 A/B 结论**都不可靠**（`DS4_AHEAD=0` 被误判就是这么来的）；
- 以后配置对比必须 **每个配置 ≥3 轮**，且以**三 prompt 的均值**判断，或直接用阶段表（GPU 事件）这种低方差指标（cpu-lane wait 22.35 ± 0.04）。
