| 事实 | 值 |

| 每 token 阶段表 | cpu-lane wait **27–33 ms** / down+post 12.3 / attn proj 7.9 / routing+shared 7.6 / attn tail 6.6 / experts gate-up 2.5 / sparse attn 1.9 / comp+idx 1.4（合计 ≈68 ms） |

### 2.2 排除掉的五条路（别再试）

| # | 假设 | 怎么否掉的 | 结论 |
|---|---|---|---|
| 1 | 车道阻塞主机 → 挪出关键路径可到 20–22 tok/s | 读依赖链：`attention(L+1)` 依赖 `专家(L)` | ❌ 结构上不可能 |
| 2 | 线程没铺满 → 加线程/改工作项切分 | `run_nodes(ne * GB, f)`：工作项是**上百个**，不是 4–5 个 | ❌ 已铺满 |
| 3 | 算力受限 | `STRATA_DS4_LANE_FREE` 2/8/16 → **17.6 / 18.1 / 17.3 tok/s**，与核数无关 | ❌ |
| 4 | 带宽受限（38→50 GB/s，1.3×） | 同上，少一半核也不慢 | ❌ 至少不是线程并行能改善的 |
| 5 | 注意力 slab 太小 | 2048 vs 4096 完全一致 | ❌ |

### 2.3 本会话更正过的错误结论（引用前先看这里）

1. **"两段式没接管"** → 错。生产 exe 指向 11-02 20:30 编的二进制，代码 11-03 09:52 才提交，env 里的开关是 no-op。
2. **"2.51× 是缓存预热"** → 错。`tp_ab.sh` 的 `set_cfg` 从没清 `DS4_EXP_2PHASE`，反序跑时两条腿都在跑两段式。
3. **"indexer 占 82 秒的 78%"** → 部分错。真实拆分：打分 48.2 s + **wq_b 32.9 s（slab 只有 32 行）** + 其余 0.85 s。
4. **"`q_b + rope` 40.9 s"** → 错。68% 是上一 slab 的尾巴；真实是 wq_b 10.7 + rope 2.2 + 尾巴 28.1（= pump 等待）。
5. **"`CPU lane 1.6% of the experts`"** → 不可引用，见 §4 计数器 bug。
6. **62K 基线 951.5** → 偏低。稳定值是 **963–973**。

**根因都是同一类**：`prof_mark` 按标记位置算区间，标记打在循环/分支内部时相邻阶段互相串味；
而两个自报数字口径不同时（slot vs 专家）看起来就像"数据矛盾"。**优化前先做一致性检查。**

## 3. 你的方向：专家分布规则 + 跑满 PCIe

我同意这是解码最大的一条路，而且现有数字支持它。下面是算式和证据。

### 3.1 今天的账（实测 + 算式）

- 显存放得下 **1616 / 15360** 个专家 = **10.5%**（`--vram-experts 1.0`，只剩 595 MiB 空闲）
- 每 token 需要 **6 专家 × 40 层 = 240 个专家实例**
- 其中约 **216 个不驻留** → 由 **CPU 车道**从主机内存读（≈1.6 GB），**42 ms**、≈38 GB/s
- 这条路径是**单通道**：PCIe 在解码时几乎闲着（驻留的那 10.5% 早就放进去了，不搬）

### 3.2 为什么"跑满 PCIe"是对的（推断，需实测确认）

PCIe 的实测能力被低估了：**单队列探针 9.5 GB/s**，但我们自己的 hotpin 深队列实测是
**4/16/32 队列 = 23.5 / 30.5 / 35.0 GB/s（+49%）**。也就是说：

| 通道 | 能力 | 解码时用了吗 |
|---|---|---|
| 主机内存 → CPU 车道 | ≈38 GB/s（实测，天花板 49–51.6） | ✅ 全在这里 |
| 主机内存 → VRAM（PCIe） | **最高 35 GB/s**（深队列实测） | ❌ 基本闲置 |

**如果让两条通道并行**——一部分非驻留专家交给 PCIe 搬进 VRAM 由 GPU 算，其余仍走 CPU 车道——
聚合带宽可以从 38 GB/s 抬到 **38 + 35 ≈ 73 GB/s**，那 42 ms → **≈22 ms**，
token 68 → 48 ms，**解码 17 → 21 tok/s**（估算上界，实际受重叠度打折）。

### 3.3 专家分布规则是另一半

即使不并行，**提高驻留命中率**也直接减字节：

- 现在是均匀 `floor(frac × n_exp)` 每层分配（`ds4_model.dp.cpp:5437` 一带），**热度只决定选哪些**
- 预填充期间已经产出过热度数据：`place_experts` 的 heat-budget 路径（`DS4_HEAT_BUDGET=1`）**写好但默认关、且从未在解码上验证**
- 关键约束【实测】：长上下文时**每层都摸遍自己的 384 个专家**（100%），L0–19 占命中的 88.4%
  → 也就是说单层内部分布并不尖锐，**跨层**才是尖的。所以"少放几层、每层多放些"或"按层热度和"分配，
  可能比"每层均匀 10%"更优。**这条要实测，不能靠直觉。**

另外有一个直接可动的量：**ring 占 2029 MB VRAM**（208 槽 × 10.2 MB）【实测】。
那是预填充流式用的；如果解码时能压缩 ring，等于腾出约 200 个专家的位置。

### 3.4 具体怎么验（建议顺序，每步都能独立否决）

| 步 | 做什么 | 期望/判据 |
|---|---|---|
| **1** | **量 PCIe 在解码时到底闲不闲**：`DS4_PROF` 下看 xfer/ring 的等待计数；或加一个启动探针用深队列测一次（不只看 9.5） | 若 PCIe 已接近饱和 → 3.2 作废，直接转 3.3 |
| **2** | **两条通道并行**：把一部分层/专家的副本改走 PCIe→VRAM→GPU，另一部分留给 CPU 车道，两边按实测带宽配比 | 目标 68 → 55 ms（19 tok/s）即为成功 |
| **3** | **专家分布规则**：打开 `DS4_HEAT_BUDGET`，按"层热度 × 层内热度"重新分配 1616 个槽位，A/B 测正解率与解码速度 | 命中率 +10 pt 即约省 4 ms |
| **4** | **ring 缩容**：把预填充用的 2029 MB ring 在解码阶段释放，换 ~200 个专家驻留 | 需确认解码不用 ring |

### 3.5 不要忘的两件小事

- **`DS4_LANE_NOHELP`**（本轮刚加，二进制已含，未提交）：`=1` 时主机线程不参与车道批处理。
  用来判定"38 GB/s 是带宽还是主机份额"——这是 §2.2 第 3/4 条唯一还悬着的解释。
- 两处代码缺陷见 §4，修起来各一行，但会影响所有基于这些计数的判断。

## 7. 2026-11-05 补记：长会话掉速的根因已修复并收尾验证

本文件 §2 那九轮「解码全部无提速」之后，掉速的真因另有其人：**路由邮箱（`reqs`，kRing=64）
没有背压**——设备侧可以在 CPU 车道还没消费时继续发布，越过一整圈覆盖掉车道没读过的槽，
车道于是等一个永远不会来的回答（`DS4_LANE_TLOG` 直接抓到「等 request 6、槽里是 70」）。
修复是 `85d8f4a3` 的 `DS4_LANE_BP`（默认开）；病态夹具（`--cpu-threads 1`）里 BP=0 每请求必死锁、
BP=1 能跑完，见 `7e05e67b` / `ad46d128`。

真实负载上的收尾验证见 **`docs/VERIFY_2026-11-05_LANE_BP.md`**：24 请求 ×128 token 零 STALL、
解码率前后半段平坦（中位 15.2 → 14.9 tok/s），12 请求 ×512 token 中位 17.1 tok/s，
`down+post` 0.14–0.19 ms/层、swaps 全程 0；24 题准确率 24/24（此前基线 19/24）。

注意：§4 的两处计数缺陷**仍未修**，本文里基于它们的所有百分比口径依旧不可引用；
§5 的显存余量（`--vram-experts 1.0` 只剩 ~595 MiB）也仍是最现实的部署隐患。
