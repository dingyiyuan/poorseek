# 100K+ 预填充：635 → 1063 tok/s（2026-11-07）

**目标**：100K 以上上下文预填充稳定 800+ tok/s。
**结果**：达成并超出。100K **1063.1 tok/s**，132K **1027.9 tok/s**，极差 <1%。

## 起点：测量，不是猜测

生产配置已有 `DS4_EXP_2PHASE=1`（两段式专家反量化，PR #5047 那条）和 `DS4_IX_SLAB_MB=256`。
核对代码后确认 **256 MB 在 `max_context 393216` 下已经把 slab 顶到 `min(128, ...)` 的上限**
（64 MB → 32 行，256 MB → 128 行，再大也还是 128），所以 indexer 的 slab 那条线**已经吃干**。

100K 基线（pack-real，`--vram-experts 0.75`，HTTP 三次，零 KV 复用）：

| 次 | tok/s |
|---|---:|
| 1 | 617.6 |
| 2 | 624.1 |
| 3 | 626.1 |
| 中位 | **624.1** |

## 阶段分解：prof 只覆盖 61%

`DS4_PROF=1` 的 100K 阶段表（100001 tokens / 157.5 s = 635 tok/s）：

| 阶段 | ms | 占比 |
|---|---:|---:|
| sparse attention | 38,244 | 39.8% |
| engram | 24,497 | 25.5% |
| experts（含流式等待） | 18,052 | 18.8% |
| ffn mHC + router + sort | 8,020 | 8.3% |
| attn rest | 2,993 | 3.1% |
| 其余 | ~4,375 | 4.6% |
| **小计** | **96,181** | **61.1%** |

**剩下 38.9%（61.3 秒）没有归属** —— 而这个缺口正是答案所在。

## 根因：一个 workaround 吃掉了 40%

日志里一行：

```
ds4: 4 prompt chunks: every launch is waited on before the next is submitted
     (a workaround for the nc >= 3 stall; DS4_PROMPT_SYNC=0 turns it off)
```

源码注释（`ds4_model.dp.cpp:11595`）自己写着：设备在约 2,000 个 outstanding 命令后
停止退休，疑因专家流的双队列协议（compute 等 copy 流的 `ring_fill`，copy 流等 compute 的
`ring_free`）形成环。**在把这个环解开之前，每次 launch 都要等上一次完成**——注释原话
「costs ~20% of a long prompt's prefill」。

实测代价远不止 20%：

## A/B（配对，交替，同一二进制同一 100K prompt）

| 臂 | 1 | 2 | 中位 |
|---|---:|---:|---:|
| `DS4_PROMPT_SYNC=1`（现状） | 636.3 | 641.5 | **638.9** |
| `DS4_PROMPT_SYNC=0` | 885.4 | 1059.1 | ~972 |

稳定性（全部 `=0`）：

| 运行 | tok/s |
|---|---:|
| 100K #1 | 1059.2 |
| 100K #2 | 1065.3 |
| 100K #3 | 1063.1 |
| **100K 中位** | **1063.1** |
| 132K | **1027.9** |

**+67%**（1063 / 639）。首次的 885 是冷缓存，后三次稳定在 1059–1065（极差 0.6%）。

## 解码没有退化

| 配置 | `=1`（基线） | `=0` |
|---|---:|---:|
| `--dspark none` | 27.71 | **28.02** |
| `--dspark on` | 35.88 | **36.85** |

256 token，pack-mtp2，`--vram-experts 0.5`。解码路径不经过 prompt chunk 的 launch 闸门，
所以不受影响，实测也略高（噪声内）。

## 风险：这是关掉了一个 workaround，不是修好了环

`DS4_PROMPT_SYNC` 存在的理由是 nc >= 3 时设备会停摆，注释说它是「run 与死卡之间的差别」。

本次 **1×100K + 3×100K + 1×132K 共五次关闭后都正常跑完，无停摆、无输出异常**。
但这只覆盖了 4-chunk（100K）和 5-chunk（132K）两种 n_chunk，
**没有覆盖更多 chunk（>132K）、并发请求、或与 MTP 草稿同时运行**的情况。

真正的修法是让专家流的两个队列不再成环（注释指名的 `ring_fill` / `ring_free` 互等），
那才是可以默认关掉这个闸门的前提。**在那之前，`=0` 应该当作一个已知风险的加速档，
而不是新的默认值。**

## 复现

```bash
# 100K，零 KV 复用（prompt 尾部带唯一 nonce）
DS4_PROMPT_SYNC=0 tools/dsv41/prefill_bench.py 100000
```

阶段表见 `/data/measurements/2026-11-07-prefill/prof5.log`；
