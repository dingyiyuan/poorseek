## 01:55 **突破：122k 预填充 168 → 271 tok/s（+61%），解码不掉**

### 根因
122k 的阶段表显示 **`q_b + rope` 占 42.9%（310.9 s）**，而 3.2k 时只占 5.8%。原因是
`c.A = attn_slab_rows(env, chunk, base, spare, ...)` —— 注意力 slab 的批大小**按剩余显存自动选**；
长上下文 KV 变大 → `spare` 变小 → `c.A` 变成小批 → q_b 的 GEMM 被迫分很多小批，效率崩掉。

|---|---|---|---|---|---|
| 全自动 | 167.9 tok/s | 310.9 s | 21.2 | 1524 | 宽裕 |
| `DS4_ATTN_SLAB=1024` | 251.3 (+50%) | — | 18.4 (−13%) | 1490 | — |
| `DS4_ATTN_SLAB=2048` | 272.1 (+62%) | 39.5 s | 17.7 (−17%) | 1450 | — |

### 仍未解的根本问题（下一步的真解）
slab 缓冲**常驻**，只在 chunk（预填充）路径需要 2048 行，解码窗口根本用不到。

## 02:30 设计 B：预填充/解码的**分段配置**（phase split）

### 问题（一句话）
注意力 slab 的批大小 `c.A` 在**启动时**就定死了，而它只在**预填充的 chunk 路径**上有用：
- 预填充要 2048 行（否则 q_b/wo 的权重被反复解量化 32 次）；
- 解码只要 1 行，但那 2048 行的缓冲（`c.q/c.o/c.o16/c.oa/c.oa16`，每行约 `HQ*10 + OG*o_lora*6` 字节）**常驻占显存**。
现在靠 `--vram-experts 1.0` 把占用补回来，只剩 595 MiB 余量。

### 代码事实（`ds4_model.dp.cpp` 3810–3850）
```cpp
const size_t a_mb = attn_slab_base_mb(unified, a_mb_env, defaults_026());
c.A = std::max(64, (int) ((a_mb << 20) / HQ) / 64 * 64);          // base
const double bpr = HQ * 10.0 + OG * o_lora * 6.0;                  // 每行字节
double spare = (room - other_b - exp_b) / devs.size();             // 每卡剩余
c.A = attn_slab_rows(env, chunk, base, spare, bpr, ...);           // 自动/强制
```
→ 分配点在**设备初始化**里，所以 `DS4_ATTN_SLAB` 改的是启动分配，不是每次 chunk。

### 方案（低风险版，三步）
1. **把 slab 缓冲的分配/释放抽成 `slab_resize(Dev&, int rows)`**：按行数重分配
   `c.q / c.o / c.o16 / c.oa / c.oa16`（现在这几块在初始化里一次性分配）。
2. **阶段切换时重算**：
   - 进入 prompt（第一个 chunk 前）：`rows = min(2048, fit(room_now))`，调 `slab_resize(rows)`；
   - prompt 结束（转为解码前）：`slab_resize(base)`，把省下的显存**让给专家环**——
     如果专家槽是静态数组，则至少让下一次启动能用 2048 行 slab + 更多槽；
     若槽位可动态扩容，则直接扩槽。
3. **开关**：`DS4_PHASE_SPLIT=1` 才启用（默认关，保证现有行为不变）。

### 预期
- 预填充保持 271 tok/s（122k）；
- 解码从 21.2 回到 **22–23**（拿回被 slab 占的显存，专家槽 1616 → 更多）；
- 长上下文余量从 595 MiB 回到 ~2 GB，降低 OOM 风险。

### 风险
- 显存重分配若与专家 swap 线程竞争，可能出现释放后仍被引用的窗口 →
  **必须**在 phase 切换点（没有在飞拷贝时）做，并加断言/睡眠等待。
- 验证方式：先在 `DS4_PHASE_SPLIT=1` 下跑 3 轮解码 + 一次 122k 预填充，对比 21.2 / 271。

### 明天的测试清单（服务已停，GPU 空闲但今晚不启动）

## 02:40 CED（20 编码器 + 20 解码器）的核查结论

### 引擎现状
- 引擎**没有** CED 逻辑，40 层 [0,39] 对预填充和解码一视同仁。
- 但有一个探针开关：**`DS4_PREFILL_LAYERS=N`**（`run_set()` 开头 `if (l.il >= kPfLayers) return true;`），
  作用只是**跳过 N..39 层的专家阶段**。作者注释原话：
  > "A knob for the CED claim about V4.1-Flash (20 causal-encoder + 20 decoder layers, the decoder half only
  > seeing a 128-token tail): **if that were how this engine's model behaves**, skipping 20..39 would leave the
  > first token unchanged and halve the work."
  → 它**不改变 KV 生成**，只省专家计算，输出会是错的；是"量一下 CED 能省多少"的探针，不是 CED 实现。

### 权重核查（纯文件检查）
基础模型 1008 个张量、41 种层内角色：`attn_*`、`attn_compressor_*`、`indexer.*`、`ffn_*`、`engram_*`、`hc_*`。
**没有** `enc_to_dec` / `ced` / `cross` / `decoder_kv_proj` 这类 CED 专用投影权重。

### 推论（重要）
如果 CED 的"后 20 层 KV 由第 20 层隐藏状态投影生成"成立，那它**不需要新参数**：
每层本来就有自己的 `attn_kv`，即 `KV_i = attn_kv_i(h20)`（i = 20..39）。
所以 CED 预填充是**引擎路径问题**，不是模型权重问题——**可以实现**。

### 正确的 CED 预填充应该长什么样
1. L0–L19：对全部 prompt token 正常算（attention + MoE + KV）；
2. 取 L19 的输出 `h20`；
3. L20–L39：**不做逐 token 的 attention/MoE**，只对 `h20` 做一次 `attn_kv_i` 投影得到 KV（i=20..39）；
