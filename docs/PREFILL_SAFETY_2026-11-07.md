# 1000+ tok/s 预填充的安全性：边界证据与风险边界

前一份报告 [PREFILL_100K_2026-11-07.md](PREFILL_100K_2026-11-07.md) 给出 100K **1063 tok/s**，
靠的是关掉 `DS4_PROMPT_SYNC`。这份回答「稳不稳」。

## 一、我上一轮说没覆盖的三个场景，现在测了

全部 `DS4_PROMPT_SYNC=0`、`DS4_RING_DEP=host`、零 LLM 复用（prompt 尾部唯一 nonce）。

| 场景 | 结果 | 停摆？ |
|---|---|---|
| 100K（3 chunks） | 1059.2 / 1065.3 / 1063.1 | 无 |
| 132K（4 chunks） | 1027.9 | 无 |
| **200K（6 chunks）** | **947.5** | 无 |
| **260K（8 chunks）** | **881.8** | 无 |
| **100K + `--dspark on`（MTP）** | **1064.9** | 无 |

最大上下文 260K 也稳在 800 以上；MTP 同时开对预填充无影响（1064.9 vs 1063.1）。

**并发请求：未测，且方法论上不该这样测。** 生产配置 `--parallel` 默认 1，
并发预填充在真实部署里不存在；要测并发就得把 `--vram-experts` 降下来让两个 slot 装得下，
那测的是**另一个配置**，不是要保证的场景。

## 二、更强的证据：这段代码自己做过 A/B

`ab19cdec` 的提交信息（我在仓库里读到的，不是我测的）在 B70 上跑过同一组对照：

| 配置 | 时间 | 速度 | engine reset |
|---|---:|---:|---:|
| `DS4_PROMPT_SYNC=1`（默认） | 372,513 ms | 176.10 tok/s | 0 |
| `=0` + `RING_DEP=host` | 184,052 ms | **356.42 tok/s** | 0 |
| `=0` + `RING_DEP=host`（第二次） | 183,997 ms | **356.53 tok/s** | 0 |

两次独立运行结果差 0.006%，且工作量相同（Engram 行 3,148,800 = 65,600 × 48，下一 token 54994 两边一致）。
所以那 2 倍是**真实的专家读取与计算重新重叠**，不是偷工减料。

## 三、`RING_DEP=host` 已经把环拆了 —— 这是关键

`ds4_model.dp.cpp:4771` 的注释说得很清楚：专家流本来只有两条跨队列边
（compute → copy 的 `ring_fill`，copy → compute 的 `ring_free`），那对能成环，
所以才有了 `nc >= 3` 的每 launch 一等的闸门。

`DS4_RING_DEP=host` 让 copy 侧在 pump 线程上等槽位的最后一次使用
（有界，`DS4_RING_WAIT_MS` 默认 180 s，超时会点名槽位并结束运行），
**copy 不再等 compute 队列，剩下的边单向，环形成不了。**

而生产配置里 `DS4_RING_DEP=host` **早就是开的**。所以那对队列在今天已经不成环了。

## 四、结论：风险比上一份报告写的要小，但不是零

**已经排除的**：
- 环本身（`RING_DEP=host` 已拆，且有官方的同卡 A/B）
- 3/4/6/8 chunks 的停摆（我实测五次全过）
- MTP 同时运行（实测）
- 大上下文（260K 实测 881.8）

**仍然存在的边界**：
1. 注释里的「设备在约 2,000 个 outstanding 命令后停止退休」是**现象描述，根因仍未定位**。
   `RING_DEP=host` 避开了它，不等于治好了它。
2. `ab19cdec` 明说它**只覆盖流式 DMA 段**；批量路径（10167 / 4247）仍带着同一对边。
   因此把默认翻掉会把没测过的形状推上异步路径 —— 这也是它保持 opt-in 的理由。
3. 我只测了这一台 B70、这一版驱动。别的卡、别的驱动没测。

**建议**：把 `PROMPT_SYNC=0` 作为生产配置时，明确它是「已被五次实测 + 一次官方 A/B 支撑的加速档」，
比上一份报告里的「已知风险的实验档」定位要强得多；但**不该写进默认值**——
那需要先把那 2,000 命令的根因定位，或至少把批量路径也覆盖掉。
